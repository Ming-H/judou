## 1. 产品定位

### 1.1 一句话

> 开源的 AI 财报伴读器：拖入或一键下载财报 PDF，像读书软件一样阅读原文；AI 提供逐页速览、数字翻译、划词问答；并能**跨多份财报/公告做事件梳理**（如新签订单追踪）。

### 1.2 三种使用形态（同一代码库）

| 形态 | 场景 | 说明 |
|---|---|---|
| **在线版**（主打） | 打开网站 → 注册 → 导入/下载财报 → 阅读 | 部署在 Vercel/Cloudflare 免费层 |
| **自部署版** | 用户 clone 后本地跑 | `docker-compose up` 或 `python main.py`，数据全本地 |
| **纯前端版**（降级） | 不注册也能用核心功能 | PDF.js 全浏览器端解析 + 用户自己填 LLM key |

三种形态共用核心包（解析/索引/提示词），是开源项目常见的 **"cloud + self-host" 双轨**，也是获客漏斗：访客（纯前端试用）→ 注册用户（云端便利）→ 极客（自部署）。

### 1.3 核心原则（继承 v1，不变）

1. 用户始终在读原文——AI 是伴读不是替读
2. AI 只做有依据的解释——回答必须引用页码
3. 数字由程序计算，AI 只说人话

## 2. 竞品调研结论（为什么这个定位有空间）

### 2.1 竞品地图

| 竞品 | 类型 | 核心能力 | 与我们的差异 |
|---|---|---|---|
| [MinerU](https://github.com/opendatalab/MinerU) | 开源 PDF 解析 | PDF→Markdown/JSON，登顶 Trending | 它是**解析层基建**，不是阅读产品；我们可将其作为解析引擎之一接入 |
| [Annual-Report-Reader](https://github.com/arjun-ms/Annual-Report-Reader) | 开源年报问答 | Langchain+Chroma 向量问答 | 只做问答，无阅读体验；无中文优化；无数字翻译 |
| [扣子空间财报分析](https://space.coze.cn/vibe/ai-statement-analysis) | 商业 AI | 上传→10 分钟出分析报告 | 是**替代读**的路线（生成报告），我们做**辅助读**；且不开源 |
| 腾讯元宝长文精读 | 商业 AI | 通用长文+财报模块 | 通用产品无财报专属能力（科目词典/单季拆分/公告追踪） |
| ChatDoc / KIMI 等 | 商业 AI | 通用 PDF 对话 | 同上；财报数字精度与引用无保障 |
| 财报阅读器（Chrome 插件） | 插件 | 网页财报转纯文本喂 AI | 无自有阅读器，体验割裂 |
| 东方财富/问财 | 数据平台 | 查数据 | 不是"读原文"场景 |

### 2.2 差异化结论（我们的护城河）

调研后确认的空白点，按价值排序：

1. **「阅读体验 × 财报特化」组合无人做**：读书软件的形态（逐页/书签/划线）+ 财报特化（数字翻译/单季拆分/科目词典）——商业 AI 在生成报告，开源项目在做解析，没人做"舒服地读"
2. **多文档事件梳理是空白**：竞品都是单文档问答。"把这家公司近 8 个季度财报 + 全部公告做成时间线，追踪新签订单/合同负债变化"——这恰是投资者真实工作流（见 §5 新功能）
3. **开源 + 中国数据源**：开源竞品无巨潮集成；商业产品不开源。中文财报场景（巨潮/问财/A 股口径）做深，是天然区隔

**竞品策略**：不做 PDF 解析轮子（可接 MinerU/自研轻量规则），专注「阅读层 + 财报理解层 + 多文档层」。

### 4.1 账户与云（v2 新增）

**认证**：
- 邮箱+密码注册/登录；支持 GitHub OAuth（开源项目的社区惯例，降低注册门槛）
- 免费层策略（控成本的关键）：
  - 匿名用户：纯前端功能（阅读+单位换算），不消耗服务端 LLM
  - 注册免费用户：每月 N 次 AI 速览/问答配额（如 30 份文档预处理 + 500 次问答）
  - BYOK 模式：用户填自己的 LLM key（GLM/OpenAI/Claude）→ 配额无限，成本归用户——**这是开源+免费运营的解法**：服务器默认 key 只做体验额度

**存储**：
- 用户文档库：每用户默认 200MB（财报 PDF 平均 1-2MB，够存百份）
- 阅读进度/笔记/划线：云端同步

### 4.2 文档库与工作区（v2 新增）

- **文档库**：已导入财报的列表视图（公司/报告期/类型/阅读进度/预处理状态）
- **公司聚合**：同一公司的多期财报自动归组（`松发股份 → 2025年报/2026一季/2026中报...`）
- **工作区**：从文档库勾选多份文档 → 进入「梳理模式」（§5）

### 4.3 F2 增强：站内下载财报

在 v1 巨潮下载基础上：
- 搜索结果直接入库（不需要先下载到本地再传）
- 支持「一键拉取该公司全部历史财报」按钮（投资者建仓研究的高频动作）
- 下载源记录（公告 URL/日期），保证可溯源

## 5. ★ 多文档 AI 梳理（v2 核心新能力）

> 需求原点：用户原话——"可以对多个财报或者公告进行梳理，给出指导，比如新签订单等"

### 5.1 功能定义

在**公司工作区**（或自选多份文档）中，AI 跨文档回答三类问题：

**A. 事件时间线（公告梳理）**
```
输入：松发股份 2025.8 - 2026.9 的全部公告（24 份）+ 3 份财报
输出：
━━━ 松发股份 事件时间线（AI 生成，附原文链接）━━━
2026-09-01 [订单] 广船国际…（注：此为示例格式）
2026-08-25 [财报] 中报发布：H1 营收 235 亿 +252%
2026-07-29 [融资] 定增 4794 万股落地
2026-05-20 [订单] 新接 207 艘船，高附加值占 72%
...
可筛选：[订单] [融资] [减持/解禁] [业绩] [风险]
```

**B. 跨期科目追踪（财报梳理）**
```
"合同负债的近 5 期变化"
2025Q3: 50.7亿 → Q4: 53.5亿 → 2026Q1: 82.7亿 → Q2: 120.4亿 (+46% 环比)
AI 注解：连续 4 期上升，供不应求信号增强 [引：各期财报 Pxx]
```

**C. 综合导读（给指导）**
```
"我该重点读这家中报的哪几节？为什么？"
AI：基于近三期财报差异 + 近期公告事件，指出 3-5 个值得精读的章节及原因
（例：「应收激增 38% 超营收增速 → 建议精读 P87 现金流量表附注」）
```

### 5.2 实现设计

**数据层**：
- 公告获取：复用巨潮搜索接口（按公司+日期范围拉公告列表+PDF）
- 事件抽取：规则层（标题关键词分类：订单/合同/中标→订单类；减持/解禁/质押→筹码类...）+ LLM 层（正文里抽事件结构 `{日期, 类型, 主体, 金额, 摘要, 页码}`）
- 跨期科目：各期财报预处理时已建数字索引，按科目名聚合即得时间序列

**AI 层**：
- 梳理任务 = 把多份文档的结构化产物（数字索引+事件列表）作为上下文，让 LLM 做汇总/解释——**不是把 10 份 PDF 原文塞进上下文**（超长且贵），结构化聚合是唯一可行路径
- 输出仍强制引用（每条事件/数字带文档名+页码）

**成本**：事件抽取按公告数计（每份公告一次调用），典型公司季度约 20-50 份公告 ≈ 数万 token，可控。

### 5.3 与现有工作流的呼应（内部自用价值）

此功能即「跟踪信号产品化」：合同负债环比（松发核心跟踪数）、新签订单公告（如中国船舶 9/1 的 10 亿美元 PCTC 单）正是投资纪律中的信号源。自用即最初用户。

## 6. 技术方案（v2 架构）

### 6.1 总体架构（云部署版）

```
┌─ 前端 SPA（Next.js，部署 Vercel）──────────────┐
│  阅读器(PDF.js) / 文档库 / 工作区 / 梳理视图 / 账户 │
└──────────────┬───────────────────────┘
               │
┌─ API 层（Next.js API Routes 或独立 FastAPI）────┐
│  auth(RBW/next-auth)  docs CRUD  cninfo  ask/mix │
└──┬────────────┬──────────────┬────────────┘
   │            │              │
┌─ DB ──┐  ┌─ 对象存储 ─┐  ┌─ 任务队列 ──────┐
│用户/文档│  │PDF+预处理JSON│  │预处理/梳理(异步) │
│元数据  │  │(R2/S3 免费层)│  │(Vercel Cron 或   │
└───────┘  └───────────┘   │ 队列服务)        │
                           └───────┬────────┘
                                   │
                        ┌─ LLM 网关（接口抽象）──┐
                        │ GLM / OpenAI / Claude   │
                        │ 用户 BYOK 或平台 key     │
                        └────────────────────┘
```

### 6.2 免费层部署可行性（调研结论）

| 组件 | 方案 | 免费额度 | 结论 |
|---|---|---|---|
| 前端+API | **Vercel Hobby** | 100GB 流量/月，Serverless 10-60s 执行 | ✅ 够 MVP；注意 Serverless 不能跑 5 分钟的预处理 |
| 长任务（预处理） | **方案 a**：Vercel Background Functions（需 Pro）；**方案 b（推荐）**：预处理拆成每页一个短任务逐个触发；**方案 c**：浏览器端跑（WebAssembly PDF 解析）| — | V1 采用 b：逐页触发、进度条、无长任务 |
| 数据库 | **Supabase 免费层**（Postgres 500MB + Auth 自带）或 **Cloudflare D1** | 500MB | ✅ Supabase 一站式解决 auth+db，省一个组件 |
| 对象存储 | **Cloudflare R2**（10GB 免费，零出口流量费） | 10GB | ✅ 存 PDF 与预处理 JSON |
| LLM | 平台 key 限额 + **BYOK**（用户自带 GLM/OpenAI key 存于自己账户，加密存储） | — | BYOK 是免费运营的关键设计 |
| 备选 | Railway/Render 容器（适合自部署文档场景） | 有限免费 | 写进 README 的自部署指引 |

**成本模型**（最坏估计）：100 活跃用户 × 月 10 份财报 × 0.5 元 LLM = 平台 key 成本 500 元/月。启动期由 BYOK 分流（预计 70% 重度用户会自带 key），实际平台成本可控在百元级；超出则配额收紧——**先免费跑通，产品验证后再考虑捐赠/付费 BYOK 增值**。

### 6.3 技术栈定版

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **Next.js 14+ (App Router) + TypeScript** | Vercel 亲儿子，SSR+API 一体；开源项目主流栈利于贡献 |
| 阅读器 | PDF.js（react-pdf 封装） | 文本层能力是 F3 悬浮的根基 |
| UI | Tailwind + shadcn/ui | 快速出活，开源观感 |
| DB/Auth | Supabase（Postgres + Auth + RLS） | 免费层 generous；GitHub OAuth 现成 |
| 存储 | Cloudflare R2 | 免出口费 |
| LLM | 自建薄网关层（统一接口），默认 GLM，BYOK 可换 | 避免锁定 |
| 解析 | pypdf（轻量）→ 复杂版面接 MinerU（可选依赖） | 渐进式 |
| 部署 | Vercel（云）+ docker-compose（自部署） | 双轨 |

### 6.4 开源工程规范（面向 GitHub）

- **协议**：AGPL-3.0（防云厂商白嫖闭源；对个人使用无碍）或 MIT（更友好但可被商业套壳）——**建议 AGPL-3.0**，README 说明
- 仓库结构：`apps/web`（Next.js）+ `packages/core`（解析/索引/提示词，纯 TS/或 Python sidecar）+ `docs`
- CI：GitHub Actions（lint/test/preview deploy）
- 贡献指南 + 中英双语 README + Issues 模板（财报解析 bad case 收集模板——开源社区帮我们积累测试集）
- 命名：待定（建议中英皆可读，如 `FinReader` / `ReportPal` / `财报伴读`）

## 8. 风险与对策（v2 增补）

| 风险 | 对策 |
|---|---|
| 巨潮接口被限流/封（站内下载是核心卖点） | 接口层抽象可换源；缓存已下载公告；失败降级引导手动上传；监控+告警 |
| LLM 成本失控（免费用户滥用） | 配额 + 速率限制 + BYOK 引导 + 单文档 LLM 预算上限 |
| Serverless 时限 vs 预处理时长 | 逐页任务化（6.2b）；单页失败可重试不阻塞整本 |
| 合规：财报数据的转载 | 只存用户自己导入/拉取的公开公告，不做二次分发数据库；页码引用指向巨潮原文 |
| AGPL 劝退商业协作者 | README 明确双轨：核心 AGPL，可谈商业授权 |
| 与 MinerU 等基建重复 | 定位为"可插拔解析引擎"，MinerU 是可选依赖不是竞品 |
| 幻觉（梳理场景更敏感） | 事件/数字全部来自结构化抽取层，LLM 仅做汇总叙述；每条带引用；设置用户反馈纠错入口 |
